# 레퍼런스 분석 (OpenCV)

"이 영상처럼 만들어 주세요"라는 요청은 보통 질감보다 움직임과 편집 때문에 나옵니다. 그런데 눈으로 본 인상은 숫자로 옮기지 않으면 계획에 들어가지 않고, 렌더가 맞았는지도 판정할 수 없습니다. 이 단계는 레퍼런스 영상을 OpenCV로 분해해 숫자로 남기고, 계획·타이밍·질감이 그 숫자를 인용하게 만듭니다. 렌더가 끝나면 같은 도구로 렌더를 재서 목표와 비교합니다.

![레퍼런스 분석 파이프라인](../../../docs/assets/ref-pipeline.png)

## 실행

```bash
python3 -m venv .venv-ref
.venv-ref/bin/pip install -r "$SKILL_ROOT/scripts/requirements-ref.txt"
mkdir -p "$PROJECT_ROOT/ref" "$PROJECT_ROOT/qa"
.venv-ref/bin/python -I "$SKILL_ROOT/scripts/ref-analyze.py" reference.mp4 \
  -o "$PROJECT_ROOT/ref/analysis.json" --targets "$PROJECT_ROOT/ref/targets.json"
cp "$SKILL_ROOT/templates/ANALYSIS.md" "$PROJECT_ROOT/ref/ANALYSIS.md"   # 숫자를 옮기고 뜻을 채운다
python3 "$SKILL_ROOT/harness/gate.py" ref "$PROJECT_ROOT"
```

- 의존성은 `requirements-ref.txt`에 정확한 버전으로 고정돼 있습니다. 2026-10-24에 Python 3.14에서 확인했습니다. numpy 2.2.x는 Python 3.14에서 같은 프레임을 매번 다른 값으로 읽었습니다(지원하지 않는 조합). 버전을 바꾸면 같은 영상을 두 번 분석해 값이 같은지 먼저 봅니다.
- `-I`는 현재 폴더의 파이썬 파일을 불러오지 않게 합니다. 받은 영상 옆에서 실행해도 안전합니다.
- 36초짜리 540x960 영상 하나에 노트북에서 약 1분 걸립니다.
- 레퍼런스 영상과 그 프레임은 저장소에 커밋하지 않습니다. `ref/`에는 숫자(`analysis.json`, `targets.json`, `ANALYSIS.md`)만 둡니다.

## 렌더 후 비교

```bash
.venv-ref/bin/python -I "$SKILL_ROOT/scripts/ref-analyze.py" "$PROJECT_ROOT/out/final.mp4" -o "$PROJECT_ROOT/qa/render-analysis.json"
python3 "$SKILL_ROOT/harness/gate.py" ref "$PROJECT_ROOT"
```

게이트는 `targets.json`의 지표마다 `목표, 값, 몇 % 차이, 허용 범위`를 한 줄씩 적고, 하나라도 허용 범위를 벗어나면 종료 코드 1로 끝납니다. 렌더 분석이 최종본보다 오래됐으면 비교하지 않고 막습니다. 게이트는 완성된 mp4만 재기 때문에 Remotion, HyperFrames, 손 편집 어느 쪽으로 만들었든 같은 방식으로 동작합니다. 허용 오차를 한꺼번에 넓히거나 좁히려면 `GATE_REF_TOL_SCALE`을 씁니다. 지표별로 바꾸려면 `targets.json`을 고치고 `ANALYSIS.md`에 이유를 적습니다.

## 지표

모든 프레임은 짧은 변을 540px로 줄인 뒤 잽니다. 크기가 다른 영상끼리 비교하려는 것입니다. 움직임 지표(프레임 간 차이, 흐름)는 1/30초당 값으로 바꿔 적습니다. 그래서 54fps 레퍼런스와 30fps 렌더를 그대로 비교할 수 있습니다. 같은 애니메이션을 60fps(Remotion)와 30fps(HyperFrames)로 렌더해 확인했고, 12개 지표가 모두 허용 범위 안이었습니다(흐름 −17%, 블러 +50%로 허용 한계, 2px과 3px의 한 칸 차이, 나머지 ±3% 이내). 기준값(정지 판정, 컷 판정)과 단위는 `analysis.json`의 `thresholds`, `units`에 함께 기록됩니다.

### 편집 리듬

| 지표 | 쉬운 말 | 재는 방법 | 다르면 고칠 것 |
|---|---|---|---|
| `edit.cuts`, `cutCount`, `cutsPerMin` | 화면이 통째로 바뀐 시각 | 앞 프레임과의 HSV 히스토그램 상관(`cv2.calcHist`, `cv2.compareHist` CORREL)이 0.6 아래이거나 평균 밝기 차(`cv2.absdiff`)가 25를 넘는 프레임. 0.1초 안에 이어진 것은 하나로 합칩니다 | 컷이 적으면 장을 더 쪼개고, 몰아치는 구간(짧은 컷이 이어지는 곳)을 만듭니다 |
| `edit.shotMeanS`, `shotCV` | 컷 하나의 평균 길이와 길이가 얼마나 들쭉날쭉한지 | 컷 사이 간격의 평균, 표준편차 ÷ 평균 | CV가 낮으면 모든 컷 길이가 비슷한 슬라이드쇼입니다. 짧은 컷과 긴 홀드를 섞습니다 |
| `edit.stillShare` | 거의 안 움직이는 프레임의 비율 | 앞 프레임과의 평균 밝기 차(1/30초당)가 1.0 미만인 프레임 수 ÷ 전체 | 정지 프레임이 너무 많으면 홀드를 줄이거나 홀드 중에도 천천히 미는 움직임을 넣습니다. 너무 적으면 읽을 시간을 줍니다 |
| `edit.holds`, `holdMeanS`, `holdLongestS` | 0.25초 이상 이어진 정지 구간 | 정지 프레임이 이어진 길이 | 홀드가 레퍼런스보다 길면 줄이고, 가장 긴 홀드는 핵심 문장 하나에만 씁니다 |
| `edit.meanDiff` | 화면이 얼마나 바뀌는지의 평균 | `cv2.absdiff` 평균(0-255), 1/30초당으로 환산 | 낮으면 전체가 느리게 느껴집니다. 전환을 빠르게 하거나 화면 안의 움직임을 늘립니다 |

### 움직임

| 지표 | 쉬운 말 | 재는 방법 | 다르면 고칠 것 |
|---|---|---|---|
| `motion.meanFlow`, `p90Flow` | 화면 속 물체가 1/30초에 몇 px 움직이는지 | Farneback 광학 흐름(`cv2.calcOpticalFlowFarneback`)의 크기 평균. 짧은 변 270px에서 재고 540px, 1/30초 기준으로 환산합니다 | 낮으면 카메라 이동과 요소 이동을 키웁니다 |
| `motion.dominantDir` | 주로 어느 방향으로 움직이는지 (0 = 오른쪽, 90 = 아래, 180 = 왼쪽, 270 = 위) | 흐름 크기로 가중한 방향 히스토그램(45도 칸 8개)의 최빈값 | 레퍼런스가 한 방향으로 흐르면 전환 방향을 맞춥니다 |
| `motion.transitions`, `transitionPeakMean`, `transitionMovingMeanS` | 컷 앞뒤 0.25초 동안 가장 빠른 움직임과 움직인 시간 | 컷 주변 흐름의 최댓값과, 흐름이 1/30초당 2px를 넘는 시간 | 전환 피크가 낮으면 휙 넘기는 카메라(whip)를 더 길고 빠르게 만듭니다. 컷이 움직임 없이 툭 바뀌면 이 값이 0에 가깝습니다 |
| `blur.alongPx`, `acrossPx`, `anisotropy` | 빠르게 움직이는 프레임에서 번짐의 길이와 방향성 | 흐름이 1/30초당 4px를 넘는 프레임의 고주파 밝기(밝기 - `cv2.blur` 9x9)에서, 움직임 방향과 그 수직 방향의 자기상관이 0.5 아래로 떨어지는 거리(px) | 레퍼런스보다 번짐이 짧으면 전환에 모션 블러를 넣습니다. 방향성이 1보다 크면 번짐이 움직임 방향으로 길다는 뜻입니다. 추정값이라 정밀 측정으로 쓰지 않습니다 |

### 질감

| 지표 | 쉬운 말 | 재는 방법 | 다르면 고칠 것 |
|---|---|---|---|
| `dof.bands`, `look.sharpRatio` | 화면의 위아래와 가운데 중 어디가 선명한지(심도) | 위에서 아래로 5개 띠의 라플라시안 분산(`cv2.Laplacian`)을 가장 선명한 띠로 나눈 값. sharpRatio는 위아래 25% ÷ 가운데 50% | 가운데만 선명하고 위아래가 낮으면 얕은 심도입니다. 렌더가 전부 선명하면 위아래에 흐림을 넣습니다 |
| `look.rms` | 대비 | 밝기의 표준편차 ÷ 255 | 높으면 대비를 낮추고, 낮으면 올립니다 |
| `look.sat`, `look.chroma` | 채도와 색 농도 | HSV 방식 채도 평균, (최대 - 최소) ÷ 255 평균. 검정에 가까운 픽셀은 sat이 불안정해서 chroma를 함께 봅니다 | 색 농도를 렌즈·색 보정 값으로 맞춥니다 |
| `look.black` | 가장 어두운 부분이 얼마나 검은지 | 밝기 1번째 백분위수(0-255) | 높으면 검정이 떠 있는(물 빠진) 느낌입니다 |
| `look.grain`, `grain` | 필름 같은 입자감 | 가장 평평한 20% 8x8 블록에서 고주파(밝기 - 3x3 평균)의 크기 중앙값 | 렌더가 너무 깨끗하면 그레인을 더합니다. h264 인코딩이 미세한 그레인을 지우므로 인코딩한 뒤에 잽니다 |

## 숫자가 말하지 않는 것

- 글자를 읽을 수 있는지, 타이포그래피가 장마다 바뀌는지, 캐릭터가 변형됐는지는 숫자로 잡히지 않습니다. 컨택트 시트를 직접 봅니다.
- 컷 검출은 히스토그램과 밝기 차로 하므로, 색이 같은 장끼리 밀려 들어오는 전환은 컷으로 안 잡힐 수 있습니다. `ANALYSIS.md`에 눈으로 센 장면 수를 함께 적습니다.
- 컷은 한 프레임에서 일어나므로 컷 판정(평균 밝기 차 25)은 fps로 환산하지 않습니다. fps가 아주 낮은 영상에서는 빠른 움직임이 컷으로 잡힐 수 있습니다.

## 실제 예시: 36초 9:16 레퍼런스와 첫 렌더

단어 하나를 여러 장면이 차례로 넘겨받는 36초짜리 9:16 레퍼런스(540x960, 약 54fps)와, 같은 형식으로 만든 25초짜리 첫 렌더(1080x1920, 30fps)를 같은 명령으로 분석했습니다. 2026-10-25 측정입니다.

| 지표 | 레퍼런스 | 첫 렌더 | 읽은 것 |
|---|---|---|---|
| 컷 수 / 분당 컷 | 51 / 84.1 | 14 / 33.6 | 장이 바뀌는 빈도가 절반 이하입니다 |
| 평균 컷 길이 / CV | 0.70초 / 4.81 | 1.67초 / 2.13 | 레퍼런스는 0.11~0.13초 컷이 몰아친 뒤 긴 홀드로 갑니다 |
| 정지 프레임 비율 | 62.0% | 73.3% | 렌더가 더 오래 멈춰 있습니다 |
| 평균 홀드 / 가장 긴 홀드 | 0.94초 / 4.7초 | 1.39초 / 4.6초 | 렌더의 홀드가 평균 0.45초 깁니다 |
| 평균 화면 변화 (1/30초당) | 10.8 | 3.6 | 렌더가 전체적으로 3분의 1만 바뀝니다 |
| 평균 흐름 / 상위 10% (1/30초당) | 2.96 / 9.53 px | 0.74 / 2.39 px | 화면 속 움직임이 4분의 1입니다 |
| 전환 피크 흐름 / 움직인 시간 | 43.2 px / 0.27초 | 12.5 px / 0.20초 | 휙 넘기는 전환이 레퍼런스의 3분의 1 속도입니다 |
| 블러 길이 (움직임 방향 / 수직) | 3 / 2 px (방향성 1.5) | 2 / 2 px (1.0) | 렌더 전환에는 방향성 있는 번짐이 없습니다 |
| 심도 띠 (위→아래) | 0.31 0.63 0.97 0.21 0.25 | 0.23 0.39 0.97 0.45 0.13 | 둘 다 가운데가 선명합니다 |
| 대비 / 색 농도 / 검정 / 그레인 | 0.144 / 0.061 / 64.5 / 0.073 | 0.162 / 0.054 / 52.3 / 0.071 | 질감은 가깝습니다. 그레인은 거의 같습니다 |

이 숫자로 고칠 순서가 정해집니다. 질감 숫자를 더 맞추는 것보다 (1) 컷을 늘리고 짧은 컷이 몰아치는 구간을 만들고, (2) 전환의 휙 넘김을 빠르게 하고 움직임 방향으로 블러를 넣고, (3) 홀드 사이에도 천천히 미는 움직임을 넣는 것이 먼저입니다. 첫 렌더는 정지 프레임 질감 숫자만 맞춘 상태였고, 움직임과 편집 숫자는 아무도 재지 않았습니다.
